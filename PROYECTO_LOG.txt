--------------------------------------------------------------------------------
1. QUÉ ES ESTE PROYECTO
--------------------------------------------------------------------------------

Plataforma web interna para la empresa Hardware que centraliza la gestión de
pedidos/operaciones que actualmente se registran en un Google Sheet llamado
"MainOperation".

PROBLEMA QUE RESUELVE:
  - La información llegaba por Slack/DMs/reuniones 1:1 sin estructura.
  - Errores frecuentes por datos incompletos o mal introducidos.
  - Dificultad para saber el estado real de un pedido rápidamente.
  - El Google Sheet se vuelve insostenible a medida que crece el negocio.

SOLUCIÓN:
  - Supabase como fuente de verdad (base de datos PostgreSQL).
  - Ingesta validada: Typeform → Webhook → Supabase.
  - Flujo por estados, asignación de responsables, auditoría completa.
  - Sincronización controlada hacia Google Sheets (unidireccional, Supabase → Sheets)
    mientras exista dependencia del Excel.
  - App web interna con login restringido a @qamarero.com.

3. MODELO DE DATOS (Supabase/PostgreSQL)
--------------------------------------------------------------------------------

  TABLA: orders
    - operation_id (texto único, ej: OP-2025-001)
    - customer_name, venue_name
    - purchase_type, source_department
    - amount
    - invoiced (boolean, marca si esta facturado)
    - supplier (texto, proveedor asignado)
    - bank_receipt_url
    - requester_name (nombre del solicitante interno)
    - requester_email (email del solicitante, para notificaciones)
    - ae_ref (referencia ejecutivo de cuentas)
    - shipping_address
    - status (enum: nuevo, pendiente, solicitado_a_proveedor, pagado, falta_informacion, bloqueado)
    - notes
    - phone, contact_email
    - hubspot_ref, invoice_ref
    - assigned_to
    - sheet_tab, sheet_row (para referencia cruzada con Excel)

  TABLA: order_items
    - order_id (FK → orders)
    - product_name
    - qty

  TABLA: status_history (auditoría)
    - order_id, from_status, to_status
    - changed_by, changed_at, comment

  TABLA: comments
    - order_id (FK → orders)
    - author_id (FK → user_profiles)
    - body (texto)
    - created_at, updated_at

  ROLES (enum user_role): viewer, creator, hardware, manager, admin
    - viewer: solo lectura (default para nuevos registros)
    - creator: puede crear pedidos y modificar los suyos en ciertos estados
    - hardware: acceso completo a pedidos
    - manager: lectura completa
    - admin: acceso total (incluyendo panel de administracion)

  ESTADOS (enum order_status): nuevo, pendiente, solicitado_a_proveedor, pagado,
    falta_informacion, bloqueado
    - Transiciones libres entre todos los estados
    - Auto-transicion: nuevo → pendiente al visualizar la ficha del pedido

  POLÍTICAS RLS: habilitadas para control de acceso por rol.
    - admin/hardware: ALL en orders, order_items, status_history, comments
    - manager/viewer: SELECT en todas las tablas
    - creator: SELECT/INSERT/UPDATE limitado a pedidos propios
    - viewer: SELECT en todas las tablas (sin INSERT/UPDATE/DELETE)
  SEED: estados predefinidos cargados vía migración.

--- SESION 2026-03-04 (sesion 12 — fix sincronizacion checkboxes entre admins/managers) ---

  CONTEXTO:
    - Cuando un admin marcaba el checkbox "facturado", el cambio se persistia en
      Supabase pero otros admins/managers no veian el cambio en su UI.
    - Dos causas raiz identificadas: bug de React (useState sin sync con props
      nuevos tras router.refresh) y politica RLS que no permitia UPDATE a managers.

  BUG REACT — useState SIN SINCRONIZAR CON PROPS:
    - Los componentes checkbox usaban useState(initialValue) que solo se inicializa
      en el primer mount. Cuando Realtime disparaba router.refresh() y llegaban
      props nuevos desde el servidor, useState ignoraba el valor actualizado.
    - Solucion: añadir useEffect(() => { setState(prop) }, [prop]) en 5 componentes.
    - Componentes corregidos:
      * InvoiceCheckbox.tsx (checkbox facturado en ficha)
      * OrdersTable.tsx → InvoiceCell (checkbox facturado en tabla)
      * OrderCheckbox.tsx (checkbox generico reutilizable)
      * SupplierSelect.tsx (selector de proveedor — mismo bug detectado en revision)
      * SupplierSection.tsx (wrapper de proveedor — mismo bug)
    - Componentes ya correctos (tenian useEffect): EditableField, EditableHeader,
      SearchBar.

  MIGRACION RLS — MANAGER UPDATE:
    - Politica anterior: manager solo tenia SELECT en orders.
    - Nueva politica: "orders: manager update all" → FOR UPDATE con
      USING (get_my_role() = 'manager').
    - Ahora managers pueden actualizar cualquier campo de orders (invoiced,
      proveedor, etc.).
    - Archivo: supabase/migrations/20260304000001_manager_update_policy.sql
